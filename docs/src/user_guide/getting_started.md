# Getting Started

This guide will walk you through the basics of using Eidetica in your Rust applications. We'll cover the essential steps to set up and interact with the database.

For contributing to Eidetica itself, see the [Contributing guide](../internal/contributing.md).

## Installation

Use a current Rust/Cargo toolchain (the example was tested with Rust 1.97.1), Git access to GitHub and access to crates.io for dependencies. The build also needs a native C toolchain for bundled dependencies, including SQLite. Start a new application:

```sh
cargo new eidetica-first-use --edition 2024
cd eidetica-first-use
```

Replace the `[dependencies]` section of your `Cargo.toml` with:

```toml
[dependencies]
eidetica = { git = "https://github.com/arcuru/eidetica.git", rev = "257a3202389ec9a552c959cf41914da28bd4fc7a", default-features = false, features = ["sqlite"] }
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

The revision pins the Eidetica APIs used below. Keep the `Cargo.lock` generated by the first build to pin the application's resolved dependency graph. Use `cargo build --locked` for subsequent builds.

Run async database operations inside a Tokio runtime. `#[tokio::main]` starts one for this application; an existing Tokio application can call the async methods directly. The manifest selects `sqlite` and disables the default features. The default `full` feature set also enables `postgres`, Unix `service` support and `y-crdt` (used by `YDoc`). See [Database Storage](concepts/backends.md#selecting-a-backend-via-url) for other URL and feature combinations.

## Setting up the Database

To start using Eidetica, you need to:

1. Choose and initialize a **Backend** (storage mechanism)
2. Create an **Instance** (the infrastructure manager)
3. **Create an Account and log in** (authentication and session)
4. Create or access a **Database** through the AccountSession (logical container for data)

Here's a simple example:

```rust
# extern crate eidetica;
# extern crate tokio;
# use eidetica::{Instance, NewAccount, crdt::Doc};
#
# #[tokio::main]
# async fn main() -> eidetica::Result<()> {
    // Open or initialise an Instance from a URL. `memory://` is an
    // ephemeral in-process backend — great for tests and embedded use.
    // The first user created on a fresh instance is automatically granted
    // Admin on the system databases.
    let (_instance, maybe_user) = Instance::connect_or_create(
        "memory://",
        NewAccount::passwordless("alice"),
    ).await?;
    let mut user = maybe_user.expect("memory:// is always fresh");

    // Create a database in the user's context
    let mut settings = Doc::new();
    settings.set("name", "my_database");

    // Get the default key (earliest created key)
    let default_key = user.get_default_key()?;
    let _database = user.create_database(settings, &default_key).await?;

    Ok(())
}
```

**Note**: `NewAccount::passwordless("alice")` is sugar for `NewAccount::with_password("alice", "")`. All credentials use the encrypted bundle format, but an empty password provides no meaningful confidentiality against a bundle holder. Use a nonempty password when confidentiality is needed.

The URL passed to [`Instance::connect_or_create`](../rustdoc/eidetica/instance/struct.Instance.html#method.connect_or_create) selects the backend. Some other common forms:

- `memory://` — ephemeral in-process backend (above).
- `memory:///abs/path/snap.json` — in-process backend with a JSON snapshot file (load-on-start, writes via [`Instance::flush`](../rustdoc/eidetica/instance/struct.Instance.html#method.flush)).
- `sqlite://./my_data.db?mode=rwc` — embedded SQLite database, persisted automatically. The URL is passed through to `sqlx`, so any sqlx-accepted form works (`?journal_mode=WAL`, `?busy_timeout=5000`, etc.).
- `postgres://user:pwd@host/db` — embedded PostgreSQL backend.
- `unix:///run/eidetica/service.sock` — connect to a running [daemon](service.md).

For persistent storage, follow the [SQLite CRUD walkthrough](#working-with-data). Use `Instance::connect_or_create` to bootstrap when appropriate, and `Instance::connect` when you require an already initialized instance. With SQLite, `?mode=rwc` allows creation of a missing file; reopening in the walkthrough uses `?mode=rw` instead.

## Session-Centric Architecture

Eidetica uses a user-centric architecture:

- **Instance**: Manages infrastructure (user accounts, backend, system databases)
- **AccountSession**: Handles all contextual operations (database creation, key management)

All database and key operations happen through an AccountSession after login. This provides:

- **Clear separation**: Infrastructure management vs. contextual operations
- **Strong isolation**: Each user has separate keys and preferences
- **Uniform credential storage**: Every password string, including empty, uses the same authenticated encrypted bundle

**Passwordless Users** (embedded/single-user apps):

```rust,ignore
let admin = instance.login_account("admin", "").await?;
admin.admin().await?.create_account(eidetica::NewAccount::passwordless("alice")).await?;
let user = instance.login_account("alice", "").await?;
```

**Password-Protected Users** (multi-user apps):

```rust,ignore
let admin = instance.login_account("admin", "").await?;
admin.admin().await?.create_account(eidetica::NewAccount::with_password("bob", "password123")).await?;
let user = instance.login_account("bob", "password123").await?;
```

Every login, including an empty-password login, derives the wrapping key with Argon2id and decrypts the credential bundle. Signing uses the already unlocked keys, without repeating password entry or derivation.

## Working with Data

Use a `Table<T>` to store rows under string IDs. Your row type must implement Serde's `Serialize` and `Deserialize` and be `Clone + Send + Sync`. `insert` generates a UUID string; `set` replaces the entire row at a given ID (or inserts it if absent).

Copy the following into `src/main.rs` in the [new application](#installation). Run it in that directory with no existing `people.db`. The example uses a passwordless account only for local demonstration. It commits the inserts, updates one row and deletes the other in a second transaction, then drops all handles before reopening the SQLite file. The database root ID identifies the database after reopening; a real application must retain that ID or use an [application reference](tutorial_todo_app.md#3-databases-database) to find it on a later process start.

<!-- Run this complete program in the standalone Cargo application. It opens a persistent people.db in the current directory rather than writing into the book doctest directory. -->

```rust,ignore
use eidetica::{
    Error, Instance, NewAccount, Result,
    crdt::Doc,
    store::{StoreError, Table},
};
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, Serialize, Deserialize)]
struct Person {
    name: String,
    age: u32,
}

fn assert_missing(row: Result<Person>) -> Result<()> {
    match row {
        Err(Error::Store(error)) if matches!(error.as_ref(), StoreError::KeyNotFound { .. }) => {
            Ok(())
        }
        Err(error) => Err(error),
        Ok(person) => panic!("expected a missing row, found {person:?}"),
    }
}

#[tokio::main]
async fn main() -> Result<()> {
    let (database_id, alice_id, bob_id) = {
        let (_instance, new_session) = Instance::connect_or_create(
            "sqlite://./people.db?mode=rwc",
            NewAccount::passwordless("demo"),
        )
        .await?;
        let mut session = new_session.ok_or_else(|| {
            std::io::Error::new(std::io::ErrorKind::AlreadyExists, "use a fresh people.db")
        })?;
        let mut settings = Doc::new();
        settings.set("name", "People");
        let key = session.get_default_key()?;
        let database = session.create_database(settings, &key).await?;

        let txn = database.new_transaction().await?;
        let people = txn.get_store::<Table<Person>>("people").await?;
        let alice_id = people.insert(Person { name: "Alice".into(), age: 30 }).await?;
        let bob_id = people.insert(Person { name: "Bob".into(), age: 27 }).await?;
        txn.commit().await?;

        let txn = database.new_transaction().await?;
        let people = txn.get_store::<Table<Person>>("people").await?;
        let mut alice = people.get(&alice_id).await?;
        assert_eq!(alice.age, 30);
        println!("Read after insert: {} ({})", alice.name, alice.age);
        alice.age += 1;
        people.set(&alice_id, alice).await?;
        assert!(people.delete(&bob_id).await?);
        assert_missing(people.get(&bob_id).await)?;
        assert!(!people.delete(&bob_id).await?);
        txn.commit().await?;

        (database.root_id().clone(), alice_id, bob_id)
    }; // Release the first instance and its SQLite file ownership.

    let instance = Instance::connect("sqlite://./people.db?mode=rw").await?;
    let session = instance.login_account("demo", "").await?;
    let database = session.open_database(&database_id).await?;
    let txn = database.new_transaction().await?;
    let people = txn.get_store::<Table<Person>>("people").await?;
    let alice = people.get(&alice_id).await?;
    assert_eq!((alice.name.as_str(), alice.age), ("Alice", 31));
    assert_missing(people.get(&bob_id).await)?;
    println!("Read after reopen: {} ({}); Bob is absent", alice.name, alice.age);
    Ok(())
}
```

```sh
cargo build
cargo run --locked
```

```text
Read after insert: Alice (30)
Read after reopen: Alice (31); Bob is absent
```

`get` returns `Error::Store` wrapping `StoreError::KeyNotFound` for a missing or deleted row. Don't treat every read error as absence: decoding or backend failures need separate handling. `delete` returns `true` when it stages a tombstone. The second call finds Bob already absent; in other cases `false` can also follow a failed row read. See [Table](concepts/stores.md#table) for details.

A successful `commit` persists the transaction's changes as one Entry and returns its ID. Merely staging a row change does not commit it. After a commit error, inspect the cause and the persisted state before retrying in a fresh transaction; don't assume rollback of earlier commits or blindly repeat an `insert` that generates a new ID. If initial database creation fails after genesis, `Error::created_database_id()` can identify the root for repair rather than creating another. See the [initialization contract](../design/accounts.md#initialization-and-concurrency).

A Table deletion hides the row in the current view; it does not erase earlier Entry payloads. To implement a new kind of Store rather than a new row type, see [Store Implementation Details](concepts/stores.md#store-implementation-details).
