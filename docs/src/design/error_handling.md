# Error Handling Design

Eidetica's `crate::Result<T>` defaults to `crate::Error`. Modules define their
own errors close to the operations that produce them. The crate-level enum
collects these errors so callers can handle both broad categories and specific
failures without parsing display messages.

## Conversion and classification

`List::insert` returns a `CRDTError` when the index exceeds the list length.
When a function returning `eidetica::Result` uses `?` on that result, the
explicit `From<CRDTError> for Error` implementation moves the error into
`Error::CRDT(Box<CRDTError>)`. The outer `is_crdt_error()` checks for that
wrapper; the inner `is_list_error()` identifies the bounds error specifically.

```rust
use eidetica::{
    Error, Result,
    crdt::{CRDTError, doc::List},
};

fn add_item(list: &mut List, index: usize) -> Result<()> {
    list.insert(index, "item")?;
    Ok(())
}

let mut list = List::new();
let err = add_item(&mut list, 1).unwrap_err();
assert!(err.is_crdt_error());
match err {
    Error::CRDT(cause) => {
        assert!(cause.is_list_error());
        assert!(matches!(
            *cause,
            CRDTError::ListIndexOutOfBounds { index: 1, len: 0 }
        ));
    }
    other => panic!("expected a CRDT error, got {other}"),
}
```

`#[error(transparent)]` forwards `Display` and `source()` to the wrapped
error; it does not supply the conversion. The `From` impl is what makes `?`
work in the example. Other conversions, such as those for I/O and JSON
serialization errors, are generated by `thiserror` from `#[from]`.

Classifiers are explicit matches, not a walk through the error source chain.
For example, `Error::is_not_found()` delegates to selected module errors,
whereas `Error::is_crdt_error()` checks only the outer variant.
`Error::DatabaseCreation` retains the committed root ID and the original
error after a post-genesis setup failure; inspect its `source` to classify
the original error.

## Extending the hierarchy

Adding a module error type does not register it automatically. To expose it
through `crate::Error`, add a wrapper variant and the intended conversion,
update `Error::module()`, and check which classifiers should recognize it.
When adding a variant to an existing module error, check the module's
classifiers as well as the crate-level ones. For errors that cross the service
boundary, check the wire mapping separately.

`Error` and many module enums, including `CRDTError`, are `#[non_exhaustive]`.
External matches on these enums need a fallback arm. Not every error enum has
this attribute: `entry::id::IdError` is exhaustive at this revision.

## Cost and limits

Boxing module errors such as `CRDTError` keeps the crate-wide result type
smaller at the cost of an allocation when that conversion runs on the error
path. Not every variant is boxed (`Error::State` is stored inline), and `?`
does not invoke the error conversion on success.

Structured fields can preserve details such as the list index and length, but
some variants carry `String` context created before display. Prefer variants
and classifiers for control flow, and use display text for diagnostics. The
[service error mapping](../internal/errors.md#cross-process-error-propagation)
reconstructs selected variants rather than preserving the entire local error
value. For example, there is no wire mapping back to `ListIndexOutOfBounds`:
the client receives `Error::Io` with the remote module, kind and message.
